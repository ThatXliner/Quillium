# Phase 6.5: Collab Polish - Research

**Researched:** 2026-04-17
**Domain:** CodeMirror cursor decorations, Socket.io presence events, owner disconnect detection, developer documentation
**Confidence:** HIGH

## Summary

Phase 6.5 adds three small but distinct features on top of the working Phase 6 collab foundation: live remote cursors in the editor, owner-disconnect kick with a clear toast notification, and a developer setup guide for the full collab stack.

The relay already uses Socket.io with per-room state and the client already has a working push/pull ViewPlugin. Cursor support requires two additions: a new Socket.io message type (`cursorUpdate` broadcast) on the relay side, and a new CodeMirror `StateField` + `ViewPlugin` on the client that renders `Decoration.widget` cursors at remote positions. The relay already knows `userId` per socket and can derive `isOwner` — it just needs to store that flag in `socket.data` and emit a `ownerLeft` event to the room when that socket disconnects.

The developer documentation belongs in a `docs/collab-setup.md` file at the Quillium repo root, covering both repos (Quillium + quillium-landing/relay) with copy-pastable commands for env vars, Supabase setup, relay dev startup, and Fly.io deployment.

**Primary recommendation:** Build the cursor ViewPlugin as a standalone `StateField` + `ViewPlugin` pair (not folded into `collabPlugin.ts`), add `isOwner` to `socket.data` in the auth middleware, emit `ownerLeft` from `connection.ts` on owner disconnect, and write `docs/collab-setup.md`.

## Architecture Patterns

### System Architecture Diagram

```
Client A (owner)                    Relay (Socket.io)               Client B (joiner)
  Editor                              server.ts                        Editor
    │                                     │                               │
    │─── cursorUpdate {pos, name} ───────>│                               │
    │                                     │──── cursorUpdate broadcast ──>│
    │                                     │    (to room except sender)    │
    │                                  socket.data.isOwner = true         │
    │                                     │                               │
    │─── [disconnect] ───────────────────>│                               │
    │                    handleDisconnection detects isOwner              │
    │                                     │──── ownerLeft ───────────────>│
    │                                     │                             toast.error("Owner ended session")
    │                                     │                             disableCollab(view)
```

**Cursor data flow:**

1. User moves cursor in editor → `SelectionPlugin.update()` fires
2. Plugin throttles and emits `cursorUpdate { pos: number, name: string, color: string }` via socket
3. Relay broadcasts to room (all except sender)
4. Receiving `RemoteCursorPlugin` updates `remoteCursors` StateField via dispatch
5. ViewPlugin rebuilds `DecorationSet` with one `Decoration.widget` per remote cursor

**Owner disconnect data flow:**

1. Relay auth middleware sets `socket.data.isOwner = true` when `userId === doc.owner_id`
2. `handleDisconnection()` in `connection.ts` checks `socket.data.isOwner`
3. If owner: emit `ownerLeft` to room, then proceed with existing cleanup
4. Client `collabPlugin.ts` listens for `ownerLeft`, fires `toast.error(...)`, calls `disableCollab(view)`

### Pattern 1: Remote Cursor WidgetType

The Google Docs cursor style is a thin vertical line (the caret) with a floating label above it. In CodeMirror this is a zero-width `Decoration.widget` at a document position. The widget renders a `<span>` styled as a colored caret + a `<span>` name label.

[CITED: https://github.com/codemirror/website/blob/main/site/examples/decoration/index.md]

```typescript
// Source: CodeMirror decoration examples (WidgetType pattern)
import { WidgetType, Decoration, type DecorationSet, ViewPlugin, type ViewUpdate } from "@codemirror/view";
import { StateField, StateEffect, RangeSetBuilder } from "@codemirror/state";

// One widget per remote user cursor
class RemoteCursorWidget extends WidgetType {
    constructor(readonly name: string, readonly color: string) {
        super();
    }

    eq(other: RemoteCursorWidget): boolean {
        return this.name === other.name && this.color === other.color;
    }

    toDOM(): HTMLElement {
        const wrap = document.createElement("span");
        wrap.className = "cm-remote-cursor";
        wrap.style.setProperty("--cursor-color", this.color);

        // The caret line itself (1px wide, line-height tall)
        const caret = document.createElement("span");
        caret.className = "cm-remote-cursor-caret";

        // Name label floats above
        const label = document.createElement("span");
        label.className = "cm-remote-cursor-label";
        label.textContent = this.name;

        wrap.appendChild(label);
        wrap.appendChild(caret);
        return wrap;
    }

    ignoreEvents(): boolean {
        return true; // Editor handles events, not the cursor widget
    }
}
```

### Pattern 2: StateField + StateEffect for Remote Cursor State

[CITED: https://github.com/codemirror/website/blob/main/site/docs/migration/index.md]

```typescript
// Source: CodeMirror StateField decoration pattern
import { StateEffect, StateField } from "@codemirror/state";

export type RemoteCursor = {
    clientID: string;
    pos: number;
    name: string;
    color: string;
};

// Effects for updating remote cursor state
export const setRemoteCursor = StateEffect.define<RemoteCursor>();
export const removeRemoteCursor = StateEffect.define<string>(); // clientID

// StateField holds the map of active remote cursors
export const remoteCursorsField = StateField.define<Map<string, RemoteCursor>>({
    create() { return new Map(); },
    update(cursors, tr) {
        let next = cursors;
        for (const effect of tr.effects) {
            if (effect.is(setRemoteCursor)) {
                next = new Map(next);
                next.set(effect.value.clientID, effect.value);
            } else if (effect.is(removeRemoteCursor)) {
                next = new Map(next);
                next.delete(effect.value);
            }
        }
        // Map positions through document changes
        if (tr.docChanged && next.size > 0) {
            next = new Map(
                [...next.entries()].map(([id, cursor]) => [
                    id,
                    { ...cursor, pos: tr.changes.mapPos(cursor.pos) },
                ])
            );
        }
        return next;
    },
});
```

### Pattern 3: ViewPlugin That Renders Decorations from StateField

```typescript
// Source: CodeMirror ViewPlugin + DecorationSet pattern
import { ViewPlugin, Decoration, type DecorationSet, type ViewUpdate } from "@codemirror/view";
import { RangeSetBuilder } from "@codemirror/state";

export const remoteCursorsPlugin = ViewPlugin.fromClass(
    class {
        decorations: DecorationSet;

        constructor(view: EditorView) {
            this.decorations = buildCursorDecorations(view.state);
        }

        update(update: ViewUpdate) {
            // Rebuild whenever the cursor state changes or doc changes
            if (
                update.docChanged ||
                update.state.field(remoteCursorsField) !== update.startState.field(remoteCursorsField)
            ) {
                this.decorations = buildCursorDecorations(update.state);
            }
        }
    },
    { decorations: (v) => v.decorations },
);

function buildCursorDecorations(state: EditorState): DecorationSet {
    const cursors = state.field(remoteCursorsField);
    if (cursors.size === 0) return Decoration.none;

    const builder = new RangeSetBuilder<Decoration>();
    // Sort by position so RangeSetBuilder receives them in order
    const sorted = [...cursors.values()].sort((a, b) => a.pos - b.pos);
    for (const cursor of sorted) {
        const safePos = Math.min(cursor.pos, state.doc.length);
        builder.add(
            safePos,
            safePos,
            Decoration.widget({ widget: new RemoteCursorWidget(cursor.name, cursor.color), side: 1 }),
        );
    }
    return builder.finish();
}
```

### Pattern 4: Socket.io cursorUpdate Broadcast (Relay)

The relay only needs to forward cursor updates — it does not need to store them (cursors are ephemeral, lost on disconnect). The pattern matches how `push.ts` broadcasts updates:

```typescript
// In connection.ts (relay) — new handler alongside existing ones
socket.on("cursorUpdate", (data: { pos: number; name: string; color: string }) => {
    // Broadcast to all in room except sender
    socket.to(documentId).emit("cursorUpdate", {
        clientID: socket.data.userId,
        pos: data.pos,
        name: data.name,
        color: data.color,
    });
});
```

### Pattern 6: Client-Side ownerLeft Handling

The `collabPlugin.ts` already listens to socket events in the ViewPlugin constructor. Add one more listener:

```typescript
// In collabPlugin.ts — inside ViewPlugin constructor, after existing socket.on("updates", ...)
socket.on("ownerLeft", () => {
    if (this.destroyed) return;
    // Disable collab (disconnect socket, remove extension)
    disableCollab(this.view);
    // Show toast (import from svelte-sonner, or dispatch a custom event)
    toast.error("The owner ended the session");
});
```

**Important:** `disableCollab` must be called from the ViewPlugin's update context with care — dispatching inside an update cycle can recurse. The safest pattern is a `setTimeout(..., 0)` or dispatching via `requestAnimationFrame` to let the current update complete first:

```typescript
socket.on("ownerLeft", () => {
    if (this.destroyed) return;
    // Defer to avoid dispatching inside update cycle
    setTimeout(() => {
        disableCollab(this.view);
        toast.error("The owner ended the session");
    }, 0);
});
```

### Pattern 7: Deterministic Color Assignment

Assign colors from a fixed palette based on `clientID` hash. This is deterministic — the same user always gets the same color across sessions, avoiding confusion when colors flicker on reconnect.

```typescript
// In cursors.ts
const CURSOR_COLORS = [
    "#4A90E2", // blue
    "#E87040", // orange
    "#50B86C", // green
    "#9B59B6", // purple
    "#E74C3C", // red
    "#16A085", // teal
    "#F39C12", // amber
    "#8E44AD", // violet
];

export function colorForClient(clientID: string): string {
    let hash = 0;
    for (let i = 0; i < clientID.length; i++) {
        hash = ((hash << 5) - hash) + clientID.charCodeAt(i);
        hash |= 0; // Convert to 32-bit integer
    }
    return CURSOR_COLORS[Math.abs(hash) % CURSOR_COLORS.length];
}
```

### Anti-Patterns to Avoid

- **Storing cursor data in the relay room state:** Cursors are ephemeral. Do not add them to `DocumentRoom` — they do not need DB persistence and should not survive reconnect. Relay just forwards them.
- **Dispatching inside a CM ViewPlugin update synchronously:** Calling `view.dispatch()` from within an `update()` call can recurse. Use `setTimeout(..., 0)` to defer.
- **RangeSetBuilder out-of-order insertion:** `RangeSetBuilder` requires positions to be added in sorted order (ascending). Sort remote cursors by `pos` before building.
- **Position not clamped to doc.length:** After doc changes, a cursor position may exceed `doc.length`. Always clamp: `Math.min(cursor.pos, state.doc.length)`.
- **Emitting cursorUpdate on every keystroke:** Throttle cursor emission to ~100ms intervals to avoid flooding the relay. Use a debounce/throttle in the selection change handler.
- **Sending `cursorUpdate` before collab is active:** Gate cursor emission behind the collab session being connected.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Cursor DOM rendering | Custom CSS injection or overlay div | `Decoration.widget()` + `WidgetType` | CM6 tracks document changes, maps positions, handles scroll — custom overlays go stale immediately |
| Position tracking through doc changes | Manual position rebasing | `tr.changes.mapPos(pos)` in `StateField.update` | CM's ChangeSet already knows exactly how positions shift |
| Color assignment | UUID-to-color state stored on server | Deterministic hash of `clientID` | Hash is O(n) and never needs server round-trip |
| Cursor broadcast protocol | Custom WebSocket framing | Socket.io `socket.to(room).emit("cursorUpdate", ...)` | Socket.io rooms already handle this in one call |

## Common Pitfalls

### Pitfall 1: Cursor Position Off by One After Remote Edit

**What goes wrong:** Remote cursor appears at wrong position after the owner makes an edit.
**Why it happens:** The `remoteCursorsField` update function maps positions with `tr.changes.mapPos`, but if the client processes the same transaction that applied remote updates AND the cursor update message arrives out of order, positions can drift.
**How to avoid:** In `StateField.update`, always call `tr.changes.mapPos(cursor.pos, 1)` (the `1` means "prefer the side after insertion") when a document change is present. The `side` parameter matters: `1` keeps cursors after inserted text at their position, which is the Google Docs behavior.
**Warning signs:** Cursor jumps to end of just-inserted text instead of staying where the remote user's caret actually is.

### Pitfall 2: DisableCollab Called Inside ViewPlugin Update Cycle

**What goes wrong:** Calling `view.dispatch(...)` (which `disableCollab` does) from inside a socket event handler that fires synchronously during a CM6 update causes a nested dispatch error.
**Why it happens:** Socket.io events can fire while CM is processing a transaction. `collabPlugin.ts` socket handlers run synchronously in the ViewPlugin context.
**How to avoid:** Always defer `disableCollab()` with `setTimeout(..., 0)` when triggered from a socket event inside a ViewPlugin.
**Warning signs:** `Error: Calls to EditorView.dispatch from within an update are not allowed` in the console.

### Pitfall 3: `isOwner` Not Set in socket.data

**What goes wrong:** The relay cannot tell the owner apart from collaborators at disconnect time, so `ownerLeft` is never emitted.
**Why it happens:** The current `auth/middleware.ts` computes `isOwner` but does not write it to `socket.data`. The `handleDisconnection` function in `connection.ts` only has access to `socket.data`.
**How to avoid:** Add `socket.data.isOwner = isOwner;` in the middleware after computing the value.
**Warning signs:** Collaborators never see the "owner ended session" toast; they see a plain disconnect.

### Pitfall 4: AuthenticatedSocketData Type Missing isOwner

**What goes wrong:** TypeScript raises an error when reading `socket.data.isOwner` in `connection.ts`.
**Why it happens:** The `AuthenticatedSocketData` interface in `auth/middleware.ts` declares the socket.data shape. `isOwner` is not currently in it.
**How to avoid:** Add `isOwner: boolean;` to the `AuthenticatedSocketData` interface.

### Pitfall 5: cursor CSS not applied in Tauri WebView

**What goes wrong:** Remote cursor DOM renders but is invisible because CSS classes aren't defined.
**Why it happens:** CM6 widgets render DOM but apply no default styling — all styling must come from EditorView.theme() or a global CSS rule.
**How to avoid:** Define cursor CSS via `EditorView.baseTheme()` or a global CSS block in `src/app.css`. Using `EditorView.baseTheme()` is cleaner (scoped to the editor).

```typescript
// In cursors.ts — attach to the extension array
export const remoteCursorTheme = EditorView.baseTheme({
    ".cm-remote-cursor": {
        display: "inline-block",
        position: "relative",
    },
    ".cm-remote-cursor-caret": {
        display: "inline-block",
        width: "2px",
        height: "1.1em",
        backgroundColor: "var(--cursor-color)",
        verticalAlign: "text-bottom",
    },
    ".cm-remote-cursor-label": {
        position: "absolute",
        bottom: "100%",
        left: "0",
        padding: "1px 4px",
        fontSize: "11px",
        lineHeight: "1.4",
        borderRadius: "3px",
        backgroundColor: "var(--cursor-color)",
        color: "white",
        whiteSpace: "nowrap",
        pointerEvents: "none",
        userSelect: "none",
    },
});
```

### Pitfall 6: Throttle cursorUpdate Emission

**What goes wrong:** Every keystroke or cursor move emits a socket event, flooding the relay.
**Why it happens:** CodeMirror fires `update()` on every transaction, including every character typed.
**How to avoid:** Track the last emitted position and only emit when it changes AND a minimum interval (100ms) has passed.

```typescript
// In the cursor emission ViewPlugin
private lastEmittedPos = -1;
private lastEmitTime = 0;

update(update: ViewUpdate) {
    if (!update.selectionSet && !update.docChanged) return;
    const pos = update.state.selection.main.head;
    const now = Date.now();
    if (pos !== this.lastEmittedPos && now - this.lastEmitTime > 100) {
        this.lastEmittedPos = pos;
        this.lastEmitTime = now;
        socket.emit("cursorUpdate", { pos, name: this.name, color: this.color });
    }
}
```

## Open Questions

1. **Where does the cursor emission live — collabPlugin.ts or a separate cursors.ts?**
   - What we know: `collabPlugin.ts` already has a ViewPlugin with socket access. Cursor emission needs socket + current selection.
   - Recommendation: Separate `cursors.ts` module for the cursor ViewPlugin. `createCollabExtension()` in `collabPlugin.ts` should compose both. This keeps `collabPlugin.ts` focused on push/pull OT and `cursors.ts` focused on cursor broadcast/receive.

2. **Should cursor updates be sent to the relay as a separate socket event, or piggybacked on `pushUpdates`?**
   - What we know: Cursor positions are separate from document updates. Piggybacking bloats every push message with cursor data.
   - Recommendation: Separate `cursorUpdate` event. Cursors have their own frequency (100ms) vs document updates (on docChanged).

3. **What happens to cursor display when a collaborator disconnects?**
   - What we know: On socket disconnect the relay does not emit `cursorUpdate`. The remote cursor will stay at the last known position indefinitely.
   - Recommendation: Relay should emit `clientLeft { clientID }` on any non-owner disconnect. Client removes that cursor from `remoteCursorsField`. This is a small addition to `handleDisconnection`.

4. **Should `connectedUsers` store track names for cursor labels, or should names come from the cursor update message itself?**
   - What we know: The client sends `{ pos, name, color }` in `cursorUpdate`. Name comes from the Supabase user profile or anonymous entry name.
   - Recommendation: Names travel with cursor updates. No separate `connectedUsers` store needed for Phase 6.5. The `remoteCursorsField` holds all needed state.
