## Warnings

### WR-01: Reader can throw when `versions` map contains unexpected numeric-coerced keys

**File:** `src/lib/collab/annotationSchema.ts:169-181`

**Issue:** The key filter at L171 preserves any value where `Number.isFinite(n)` is true, then looks up `versionsMap.get(String(k))`. Several string keys pass this filter but fail the roundtrip:

- `""` → `Number("") === 0` → finite → looked up as `"0"` (silent loss of the real `""` entry).
- `"1.5"` → `1.5` → finite → looked up as `"1.5"` only if written that way; a `"1.5e0"` input would be filtered as finite but looked up differently.
- Whitespace-padded keys (e.g., `" 1 "`) similarly coerce.

When `versionsMap.get(String(k))` returns `undefined` (because the source key was spelled differently), the next line `v.get("text")` throws `TypeError: Cannot read properties of undefined`. The converter contract (line 11 comment, line 107 JSDoc) promises it never throws — it returns `null`. This path violates that contract.

In-repo writers only ever use `String(idx)` with integer `idx`, so the flow is unreachable from clean-origin data, but a remote peer writing malformed keys (or future code paths adding version keys) could trigger a runtime throw.

**Fix:** Guard the lookup and bail out cleanly:
```typescript
const versions: VersionState[] = [];
for (const k of keys) {
    const v = versionsMap.get(String(k));
    if (!(v instanceof Y.Map)) {
        console.warn("[annotationSchema] Version key missing or wrong type:", k);
        return null;
    }
    const vtext = v.get("text");
    const doc = vtext instanceof Y.Text ? vtext.toString() : "";
    const label = v.get("label");
    versions.push({
        doc,
        ...(typeof label === "string" ? { label } : {}),
        annotationGeneration: 0,
    });
}
```
Or tighten the filter to require exact roundtrip: `.filter((n) => Number.isInteger(n) && String(n) === <original key>)`.

### WR-02: `activeVersionIndex` is read twice; second read races if `node` mutates between them

**File:** `src/lib/collab/annotationSchema.ts:189-192`

**Issue:**
```typescript
const rawIndex =
    typeof node.get("activeVersionIndex") === "number"
        ? (node.get("activeVersionIndex") as number)
        : 0;
```
`node.get("activeVersionIndex")` is called twice. In practice both reads are synchronous and the node isn't mutated between them, so this is latent rather than active. However:

1. It's a minor performance miss (two Y.Map hash lookups instead of one).
2. The pattern encourages time-of-check/time-of-use thinking that could bite later if observeDeep reactions ever run inside this converter's synchronous slice.

**Fix:**
```typescript
const rawIndexValue = node.get("activeVersionIndex");
const rawIndex = typeof rawIndexValue === "number" ? rawIndexValue : 0;
```

## Info

### IN-01: Unused parameter `_ytext` in `relativeToAbsolute` is re-passed through the whole converter

**File:** `src/lib/collab/annotationSchema.ts:113, 125` (and `relativePosition.ts:46`)

**Issue:** `yjsAnnotationToCodeMirror` takes `ytext` as the third argument and forwards it to `relativeToAbsolute(ydoc, ytext, ...)`, but `relativeToAbsolute` takes `_ytext` (unused, per JSDoc "kept for API symmetry"). The parameter threads through two function boundaries without being used. This isn't a bug — it's explicitly documented as "API symmetry" — but since every caller must construct/thread the `ytext` reference unnecessarily, dropping the unused argument in a follow-up cleanup would be cheaper than keeping it.

**Fix:** Either remove `_ytext` from `relativeToAbsolute` and the third argument from `yjsAnnotationToCodeMirror`, or keep the current signature and add a brief comment in `annotationSchema.ts` explaining why `ytext` is passed to a function that ignores it (currently only explained on the receiver side).

### IN-02: `(ymap as Y.Map<never>)` cast hides that the plugin is downstream-broken

**File:** `src/lib/collab/test-helpers/twoPeerHarness.ts:54`

**Issue:** The cast is correct for the planned end state (Y.Map invariance workaround after Plan 8.5b-01), but `Y.Map<never>` is an unusual target. A reader unfamiliar with the plan might expect `Y.Map<YjsAnnotationNode>` and be confused by the cast target being the uninhabited `never` type. The comment above it explains the plan trajectory but does not say why `never` specifically (vs `any` or a straight `Y.Map<YjsAnnotationNode>` cast).

**Fix:** When Plan 8.5b-01 lands, change the cast to `ymap as Y.Map<YjsAnnotationNode>` (matches the plugin's expected parameter). Until then, consider `ymap as unknown as Parameters<typeof createAnnotationSyncPlugin>[1]` which makes the "temporary bridge" nature obvious, or expand the existing comment with "`never` is used because the current plugin parameter is `Y.Map<YjsAnnotation>` which is being removed, so the most-narrow bottom type is a placeholder until 8.5b-01."

### IN-03: `thread.push(annotation.thread.map(...))` clones each message with spread; `replacements` does the same — but neither needs deep cloning of primitives

**File:** `src/lib/collab/annotationSchema.ts:66, 75`

**Issue:** `annotation.thread.map((m) => ({ ...m }))` makes a shallow copy of each `MessageObject`. Since `MessageObject` has three primitive fields (`message`, `author`, `time`), the spread is defensive — it prevents Yjs from ever aliasing a CM-layer object into the Y.Array. Same for `SuggestionReplacement` (`text`, `rationale?`). This is correct and defensible, but unusual in a codebase without a stated "never alias CM objects into Y-types" rule.

**Fix:** No code change needed. Consider adding a one-line comment: `// Spread-clone primitives; never hand CM-layer object references to Yjs to prevent accidental aliasing / later mutation leakage.`
