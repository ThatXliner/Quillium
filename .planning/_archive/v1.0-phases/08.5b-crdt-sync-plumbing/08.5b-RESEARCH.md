## User Constraints (from CONTEXT.md)

### Locked Decisions

#### Data Structure
- **D-90:** YjsAnnotation converts from plain JSON object to a `Y.Map` with children.
  Shape (recursive): `{ text: Y.Text, thread: Y.Array<MessageObject>, annotations: Y.Map<YjsAnnotation>, ...plainMetadata }`.
  Metadata fields (id, anchorPos, colorHint, activeVersionIndex, annotationGeneration, etc.) stay as plain stored values.
- **D-91:** Revision versions are stored as entries in a `versions: Y.Map<vIdx, Y.Map>`.
  Each version Y.Map has `{ text: Y.Text, annotations: Y.Map<YjsAnnotation> }`.
  No separate sibling map on the ydoc — subtrees live inside the annotation they belong to.
  (Chose "Nested inside YjsAnnotation entry" over sibling Y.Map off ydoc.)
- **D-92:** Recursive structure: annotations inside a nested editor use the same Y.Map shape.
  Same code path works at arbitrary nesting depth; no compound-scope routing needed.
- **D-93:** Comment threads are `Y.Array<MessageObject>` (append-only). No concurrent edit is possible
  because users can only edit their own messages, so conflict resolution is trivial: sort by timestamp on read.

#### Migration
- **D-94:** No migration code. Phase 8 annotation sync was never shipped to users,
  so there is no existing wire format to preserve. Phase 8.5 simply defines the new
  shape; legacy `JSON.stringify(versions)` path gets removed wholesale.

#### Undo
- **D-95:** One global `Y.UndoManager` per user, tracking `ytext` + top-level `ymap` + every
  subtree Y.Text. `trackedOrigins: new Set(["local"])` keeps it per-user (per D-74).
  Ctrl-Z walks the local stack chronologically across editors. You cannot undo other
  users' edits (standard Yjs per-user undo; nothing changes there).
- **D-96:** When Ctrl-Z undoes an edit in a nested editor that is not currently focused,
  auto-navigate/scroll to that revision so the user sees the change. Implementation: wire
  an "undo target" event from the UndoManager to the navigation system (open revision modal
  or scroll inline editor into view).
- **D-97:** Subtree Y.Texts added to UndoManager `trackedTypes` on creation. Research item:
  confirm how Y.UndoManager handles dynamically-added tracked types — may need reconstruction
  or may work via origin-only filtering. Planner/researcher to verify against current yjs docs.

#### Cursors
- **D-98:** Peer cursor rendering inside nested editors is out of scope for v1.
  Main editor cursor sync (existing Phase 7.5 awareness extension) continues unchanged.
  Nested-editor cursor sync deferred to v2 (see deferred ideas).

#### Version Switch Semantics
- **D-99:** `activeVersionIndex` is metadata about which version renders inline in the
  parent — NOT a lock on which version peers can edit. Each version Y.Text is independent;
  a peer can be typing in v0 while the owner is viewing/editing v2. Clicking a version's
  pill sets that version as active locally; there is no "owner broadcasts active version"
  ceremony. If a user wants their version to be the one rendered inline, they click its
  pill. If they change their mind, they click the other pill back.

### Claude's Discretion
- Exact Y.Map key layout for metadata fields (plain stored values) vs. Y.Map get/set semantics
- Whether `annotationGeneration` field is still needed once subtrees provide CRDT ordering
  (planner to evaluate — may be obsoleted)
- Internal origin tags for distinguishing local vs. remote subtree mutations in `NestedEditorController`
- How `createYjsBinding` reuse vs. specialization for subtrees is structured (research first)

### Deferred Ideas (OUT OF SCOPE)
- **Peer cursors inside nested editors (v2).** Extend awareness state with a `focus` field
  `{ kind: 'main' } | { kind: 'nested', revId, vIdx, relPos }` so each nested editor can render
  peer cursors whose focus matches its identity. Requires the main awareness extension to be
  scope-aware.
- **Thread message editing by original author.** If a user wants to edit their own past comment,
  that would require either converting thread entries to Y.Texts or keeping them plain but
  swapping by message id. Out of scope — the current data model treats messages as immutable
  once posted.
- **Undo auto-navigate UX polish.** When Ctrl-Z lands in a non-focused editor, we open/scroll to it.
  Future polish: toast/banner "Undid edit in revision X" for better transparency.

## Summary

Phase 8.5 replaces the current Phase 8 `JSON.stringify(versions)` workaround in `syncRevisionChanges` (src/lib/collab/yjsAnnotations.ts) with dedicated Y.Text subtrees nested inside each annotation's Y.Map representation. Every revision version becomes a Y.Map with its own `text: Y.Text` and `annotations: Y.Map<YjsAnnotation>` children; character-level CRDT merge applies uniformly at any nesting depth. The result: concurrent edits inside a nested editor merge keystroke-by-keystroke, exactly as they already do in the main doc.

The three open research questions from CONTEXT.md resolve cleanly:

1. **D-97 (UndoManager dynamic trackedTypes):** `Y.UndoManager.addToScope()` is a documented public method in yjs 13.6.30 (verified against source). Additionally, `UndoManager` tracks descendants of scoped types via `isParentOf()` — so tracking the root annotation Y.Map transitively covers every subtree Y.Text without explicit `addToScope` calls. Explicit addition still recommended for clarity and defence in depth.
2. **`createYjsBinding` reuse:** already parameterized on a Y.Text instance (line 24 of yjsBinding.ts). Works unchanged on subtree Y.Texts. No specialization needed — NestedEditorController installs the same binding alongside existing CM extensions.
3. **`annotationGeneration` obsolescence:** the field is obsoleted. With subtree ymap observers broadcasting shape changes directly (deep observation), the generation counter no longer serves a purpose. Remove from `VersionState` and `RawAnnotationsSchema`.

**Primary recommendation:** Use `Y.UndoManager` + `addToScope` for subtree registration; reuse `createYjsBinding` verbatim; model `versions: Y.Map<string, Y.Map>` keyed by version index string; expose recursive sync via a factory `createAnnotationSyncPlugin` that produces plugin instances per scope (root doc vs. any nested subtree). Guard against **yjs#642** (a known open bug affecting nested-Y.Map set+delete under undo merging) by setting `captureTimeout: 500` and emitting `undoManager.stopCapturing()` explicitly between scope-changing operations (e.g., creating/deleting versions). For concurrent-edit convergence correctness (Nyquist Dimension 5), tests MUST exercise concurrent edits on a nested subtree Y.Text with an undo in flight.

### Pattern 1: Recursive Y.Map Shape (per D-90, D-92)
**What:** Every annotation (root, nested, deeply nested) is a `Y.Map` with the same children: `text: Y.Text`, `thread: Y.Array<MessageObject>`, `annotations: Y.Map<YjsAnnotation>`, plus plain metadata.
**When to use:** All annotations. No shape variation by nesting level.
**Example:**
```typescript
// Source: [verified pattern against yjs 13.6.30 API; /yjs/yjs Context7]
import * as Y from "yjs";

function createEmptyAnnotationYMap(opts: {
    id: string;
    _type: "comment" | "revision" | "suggestion";
    startPos: Y.RelativePosition;
    endPos: Y.RelativePosition;
}): Y.Map<unknown> {
    const ymap = new Y.Map();
    // Plain metadata (stored once; "last write wins" is fine for non-conflicting fields)
    ymap.set("id", opts.id);
    ymap.set("_type", opts._type);
    ymap.set("startPos", Y.encodeRelativePosition(opts.startPos));
    ymap.set("endPos", Y.encodeRelativePosition(opts.endPos));

    // CRDT children — fresh per annotation (a Y type can only be attached once)
    ymap.set("text", new Y.Text());
    ymap.set("thread", new Y.Array());
    ymap.set("annotations", new Y.Map());

    // Revisions only: add versions map
    if (opts._type === "revision") {
        ymap.set("versions", new Y.Map());  // Y.Map<string, Y.Map>
        ymap.set("activeVersionIndex", 0);
    }
    return ymap;
}

function createVersionYMap(): Y.Map<unknown> {
    const version = new Y.Map();
    version.set("text", new Y.Text());
    version.set("annotations", new Y.Map());  // recursive: children are YjsAnnotation Y.Maps
    version.set("label", null);
    return version;
}
```

### Pattern 2: Subtree Binding via Existing `createYjsBinding`
**What:** `createYjsBinding(ytext)` accepts ANY `Y.Text`. For a nested editor, pass the subtree's Y.Text — no new code needed.
**When to use:** In `NestedEditorController.create`, after resolving the version's Y.Text.
**Example:**
```typescript
// Source: verified against src/lib/collab/yjsBinding.ts (lines 24-113)
import { createYjsBinding } from "$lib/collab/yjsBinding";

// Inside NestedEditorController.create:
const subtreeYmap = this.parentAnnotationYMap
    .get("versions")
    .get(String(this.versionIndex));
const subtreeYtext = subtreeYmap.get("text") as Y.Text;

// Install binding on nested EditorView
this.view = new EditorView({
    state: EditorState.create({
        doc: subtreeYtext.toString(),  // seed from current CRDT state
        extensions: [
            ...getExtensions({ persist: false, history: false }),
            createYjsBinding(subtreeYtext),      // ← same function, different ytext
            createAnnotationSyncPlugin(subtreeYmap, this.clientId),
        ],
    }),
    parent: host,
});
```

### Pattern 3: Dynamic `UndoManager.addToScope` (resolves D-97)
**What:** When a subtree Y.Text comes into existence (annotation creation, version add, nested annotation in a nested editor), add it to the UndoManager's scope.
**When to use:** Whenever a subtree is created locally OR observed as created remotely (for clarity — not strictly required if parent is scoped, due to `isParentOf` deep tracking).
**Example:**
```typescript
// Source: [VERIFIED: yjs src/utils/UndoManager.js raw source, Jan 2026]
// public method: addToScope(ytypes: Array<AbstractType> | AbstractType): void

// Inside NestedEditorController.create, after resolving subtreeYtext:
const undoManager = getUndoManager();  // from collab/index.ts
if (undoManager) {
    undoManager.addToScope(subtreeYtext);
    // Optional defence: also add subtree ymap for nested-annotation changes
    undoManager.addToScope(subtreeYmap);
}

// Teardown not required — UndoManager holds refs; when annotation is deleted,
// its subtree types become unreachable and stack items referencing them remain valid
// but cannot be applied (harmless; they just no-op on undo).
```

**Deep tracking fact** `[VERIFIED: /yjs/yjs source, Context7]`: `UndoManager` uses `isParentOf(scopedType, changedType)` to match events. Tracking the root annotations Y.Map transitively tracks every descendant subtree Y.Text. So explicit `addToScope(subtreeYtext)` is primarily for clarity/defence; it is not strictly required if the root is already scoped.

### Pattern 4: Recursive `createAnnotationSyncPlugin` as a Factory
**What:** The existing plugin is a ViewPlugin bound to `(ytext, ymap, clientId)`. Refactor to take the scope's ymap as the subtree root. A nested editor gets its own plugin instance operating on its subtree's ymap.
**When to use:** Once per EditorView (main or nested).
**Example:**
```typescript
// Signature (new):
export function createAnnotationSyncPlugin(
    scopeYtext: Y.Text,          // text of the scope (main doc or nested subtree)
    scopeAnnotations: Y.Map<unknown>,  // annotations living inside that scope
    clientId: string,
): Extension;

// At main editor:
createAnnotationSyncPlugin(ytext, ymap, clientId);

// At nested editor (inside NestedEditorController):
const versionYmap = annotationYmap.get("versions").get(String(vIdx));
createAnnotationSyncPlugin(
    versionYmap.get("text") as Y.Text,
    versionYmap.get("annotations") as Y.Map<unknown>,
    clientId,
);
```

### Pattern 5: Undo Auto-Navigation Event (D-96)
**What:** Wire `UndoManager` `stack-item-popped` event to the modal stack / scroll system; if the popped operation targets a non-focused nested scope, open/scroll to it.
**Example:**
```typescript
// Source: [VERIFIED: yjs UndoManager.js event payload signature]
undoManager.on("stack-item-popped", ({ stackItem, type, changedParentTypes }) => {
    // changedParentTypes: Map<YType, Array<YEvent>>
    for (const [parentType, events] of changedParentTypes) {
        // Walk up parent chain until we find an annotation Y.Map
        const ownerAnnotationId = findOwningAnnotationId(parentType);
        if (ownerAnnotationId && ownerAnnotationId !== currentlyFocusedAnnotationId()) {
            eventBus.emit("undo-target", {
                annotationId: ownerAnnotationId,
                versionIndex: resolveVersionIndex(parentType),
            });
            break;
        }
    }
});
// Listener in +page.svelte or revision controller: open modal or scrollIntoView.
```

### Pattern 6: Origin Tagging Across Nested Scopes
**What:** Every local write in any scope must use origin `"local"` so UndoManager picks it up; remote writes carry no origin (or a non-"local" origin from the wire protocol).
**Example:**
```typescript
// In NestedEditorController's binding (reused from createYjsBinding):
ydoc.transact(() => {
    subtreeYtext.delete(pos, length);
    subtreeYtext.insert(pos, inserted);
}, "local");  // Critical: matches trackedOrigins: Set(["local"])
```

### Pattern 7: Thread Append with Timestamp Sort (D-93)
**What:** Messages are appended to `Y.Array<MessageObject>` in ID + timestamp order; read path sorts by `ts` before rendering.
**Example:**
```typescript
interface MessageObject { id: string; author: string; body: string; ts: number; }

// Write:
ydoc.transact(() => {
    threadYArr.push([{ id: newId, author, body, ts: Date.now() }]);
}, "local");

// Read (in Svelte component):
const messages = $derived(
    threadYArr.toArray().sort((a, b) => a.ts - b.ts),
);
```

### Anti-Patterns to Avoid
- **JSON.stringify of subtree state.** Eliminates CRDT semantics. This is exactly the Phase 8 workaround Phase 8.5 removes.
- **Multiple `Y.UndoManager` instances.** Fragments the undo stack and breaks Ctrl-Z chronology across scopes. Use one manager + `addToScope`.
- **Reusing the same `Y.Text` instance across multiple Y.Map slots.** A Yjs shared type can be attached to exactly one position; reuse throws `yjs/create-id` error. Always `new Y.Text()` for each slot.
- **Using CodeMirror `history()` extension inside nested editors.** Phase 7.5 already replaced CM history with UndoManager. Subtrees follow suit. Double history would cause divergent stacks.
- **Reading from the main doc Y.Text to render nested content.** Nested content is the subtree's Y.Text. `annotationField` Phase-3 pushDocToVersionState becomes unnecessary.
- **Forgetting origin tag on programmatic subtree writes.** Any write without origin `"local"` is invisible to the UndoManager. Symptom: Ctrl-Z skips the edit.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Character-level concurrent text merge | Custom diff-patch merge on JSON blob | `Y.Text` | Yjs handles concurrent insert/delete intervals with stable offsets. Hand-rolled OT misses tie-breaking edges. |
| Stable position tracking across edits | Index math in annotation anchors | `Y.RelativePosition` (already used) | Y's `RelativePosition` uses item IDs, not offsets; survives arbitrary concurrent edits including deletions. |
| Per-user undo stack | Track transaction list + inverse computation | `Y.UndoManager` with `trackedOrigins: Set(["local"])` | Handles merge with remote state, operation inversion, and event emission. Origin filtering is the documented mechanism for per-user undo. |
| Deep change observation of nested types | Recursive `observe` installation | `observeDeep` on the root Y.Map | `observeDeep` fires for descendants automatically. Single subscription covers the whole annotation tree. |
| Dynamic tracking of newly-created subtree types | Reconstruct UndoManager | `undoManager.addToScope(newType)` | `[VERIFIED: yjs source]` Public API; no reconstruction needed. Also: `isParentOf` makes descendants auto-tracked if root is scoped. |
| Origin-based loop prevention | Flag variables with manual reset | `ydoc.transact(fn, "local")` + CM `Annotation` marker | Already the established pattern in yjsBinding.ts. Continue. |

**Key insight:** Yjs is a mature CRDT library; virtually every primitive Phase 8.5 needs is already implemented. The phase is architectural composition, not primitive development.

## Common Pitfalls

### Pitfall 1: yjs#642 — Nested Map Set+Delete Undo Divergence
**What goes wrong:** `[CITED: github.com/yjs/yjs/issues/642]` Still-open bug: when an UndoManager captures a transaction that both `.set(k, newYMap)` and later `.delete(k)` on a parent Y.Map, remote peers applying the undo can converge to a different state than the local peer.
**Why it happens:** The undo re-inserts the deleted entry but the nested type (a Y.Map) carries GC'd ID references on peers that saw the intermediate state. The race between replay and GC causes state forks.
**How to avoid:**
- Set `captureTimeout: 500` (already set) so rapid set+delete pairs aren't merged into one stack item.
- Call `undoManager.stopCapturing()` after any operation that creates or deletes an annotation subtree. This forces a stack boundary.
- For the "delete a revision version" flow specifically, ensure the delete is its own stack item — do NOT combine with concurrent text edits.
- Consider `ignoreRemoteMapChanges: true` ONLY if tests show convergence failures; it's experimental.
**Warning signs:** Intermittent "owner and collaborator see different text after undo" reports. Cannot be reproduced with character-by-character undo — only with structural (create/delete version) undo.
**Test coverage:** MUST include a test where Peer A creates version, Peer B starts typing in it, Peer A undoes the version creation — assert both peers converge.

### Pitfall 2: Y Type Reattachment Error
**What goes wrong:** `[VERIFIED: Yjs docs + Context7]` A shared type (Y.Text, Y.Map, Y.Array) can only be attached to one parent slot in one Y.Doc. Attempting to `.set("text", existingYText)` after `existingYText` was already a child of another map throws.
**Why it happens:** Yjs tracks parent pointers internally; reattachment would corrupt the tree.
**How to avoid:**
- Always `new Y.Text()` / `new Y.Map()` / `new Y.Array()` when setting a child.
- When "cloning" an annotation, call `clone()` recursively on children — do not share instances.
- For "move version between annotations" operations (unlikely in v1), serialize to plain, then reconstruct.
**Warning signs:** `Error: Unexpected case` or `y-crdt item already has a parent`.

### Pitfall 3: Origin Leakage Across Scopes
**What goes wrong:** A nested editor's binding writes without origin `"local"`, or a remote update is applied with origin `"local"`, corrupting the undo stack.
**Why it happens:** Easy to forget origin on programmatic writes (e.g., seeding a new version's text from the parent doc); or y-websocket's update handling must NOT use origin `"local"`.
**How to avoid:**
- Audit every `ydoc.transact(...)` in collab/* and any new nested-editor code. All local-user-initiated → `"local"`. All network-initiated → no origin or `provider`.
- Write a test that fires a simulated remote update and asserts the UndoManager's stack count is unchanged.

### Pitfall 4: Observing Deep vs. Observing Shallow
**What goes wrong:** Using `.observe` on the top-level annotations Y.Map sees only top-level key add/delete — not changes to descendant Y.Texts.
**Why it happens:** Y.Map's `.observe` is shallow by design. For nested changes, use `observeDeep`.
**How to avoid:**
- Use `ymap.observeDeep((events) => {...})` in the sync plugin.
- For binding a specific subtree Y.Text to its CodeMirror view, use `subtreeYtext.observe(delta handler)` directly — the binding IS already observing its own ytext.
**Warning signs:** "Remote peer's typing in a nested editor doesn't show up locally even though both are connected."

### Pitfall 5: `stack-item-popped` Event Requires Deep Inspection
**What goes wrong:** Wiring D-96 (undo auto-nav) to only the stack-item-popped event's `changedParentTypes` at depth 1 misses nested-in-nested edits.
**Why it happens:** `changedParentTypes` is a flat `Map<YType, Array<YEvent>>` where each key is a direct parent of a changed item — but "direct parent" means "the lowest ancestor that is a Yjs shared type," which for a nested-in-nested edit is the innermost subtree Y.Text. That's a deeply-nested node in the annotation tree.
**How to avoid:**
- Walk up via `yType.parent` chains until you hit the root annotations Y.Map and collect the annotation id from each `Y.Map` along the way.
- Prefer the OUTERMOST non-focused annotation as the scroll target (user sees where to start; nested modal opens subsequently via existing Revision flow).

### Pitfall 6: captureTimeout Merges Main + Nested Edits
**What goes wrong:** With `captureTimeout: 500` (current setting), rapid typing in the main editor followed by a quick switch to a nested editor can merge into one undo stack item spanning two scopes. Then Ctrl-Z tries to undo both, but the nested scope may not be visible.
**Why it happens:** `captureTimeout` is measured in wall-clock ms, not scope-aware.
**How to avoid:**
- Call `undoManager.stopCapturing()` on nested editor mount and on focus switch between main and nested. This forces a boundary.
- Alternative: reduce `captureTimeout` to 0 and rely solely on transaction boundaries — simpler but loses the "merge rapid typing" UX. Test both approaches.

### Pitfall 7: `annotationField` Phase-3 Still Firing After Refactor
**What goes wrong:** `pushDocToVersionState` (Phase 3 of annotationField update) copies doc text into `VersionState.doc`. After Phase 8.5 makes the subtree Y.Text the source of truth, this copy is redundant AND can thrash against the subtree.
**Why it happens:** Leftover code from pre-subtree era.
**How to avoid:**
- Remove Phase 3 entirely from `annotationField.update`.
- Remove `VersionState.doc` field (subtree Y.Text replaces it).
- Tests: assert that `VersionState` no longer carries redundant doc text after refactor.

```typescript
    ydoc: Y.Doc,

    params: {
        id: string;

        const v0 = new Y.Map();
        const v0Text = new Y.Text();

        v0.set("text", v0Text);
```

### Undo auto-nav wiring (D-96)
```typescript
// In collab/index.ts, after undoManager creation:
undoManager.on("stack-item-popped", (event) => {
    const { changedParentTypes, type } = event;
    const focusedAnnId = getCurrentlyFocusedAnnotationId();  // from Svelte store
    for (const [parentType] of changedParentTypes) {
        const owningId = findOwningAnnotationId(parentType);
        if (owningId && owningId !== focusedAnnId) {
            eventBus.emit("undo-target", {
                annotationId: owningId,
                versionIndex: findOwningVersionIndex(parentType),
                undoType: type,  // 'undo' | 'redo'
            });
            return;
        }
    }
});

function findOwningAnnotationId(yType: Y.AbstractType<any> | null): string | null {
    let cur = yType;
    while (cur) {
        if (cur instanceof Y.Map) {
            const id = cur.get("id");
            if (typeof id === "string" && cur.get("_type")) return id;
        }
        cur = (cur as any).parent ?? null;
    }
    return null;
}
```

## Open Questions (RESOLVED)

1. **RESOLVED: Should `subtreeYtext.observe` fire during `Y.UndoManager.undo()`?**
   - Decision: No new code needed — the binding's Y.Text observer fires for undo-applied deltas regardless of origin. Local undo path: `undoManager.undo()` → inverse op applied in a Yjs transaction → `ytext.observe` callback runs → `createYjsBinding` dispatches CM changes → nested CM re-renders.
   - Why: `createYjsBinding` is origin-aware via the `yjsAnnotation` CM marker and the `"remote"` origin tag for programmatic applies; local undo transactions carry neither, so the binding treats them like any other delta and round-trips them into CM. The origin check only guards against feedback loops on the CM→Y path.
   - Plan 8.5c-01 relies on this existing behaviour; no special-casing of `undoManager.origin` needed.
   - Verification: Plan 8.5a-01's `undo-manager.test.ts` scaffold includes a scenario that covers this path (local undo of a subtree edit re-renders the nested CM view).

2. **RESOLVED: What happens to a subtree Y.Text when its owning annotation is deleted from `annotationsRoot`?**
   - Decision: Call `undoManager.clear()` on document exit / collab-session teardown to release orphaned stack items.
   - Ownership: Plan 8.5c-01's `NestedEditorController.destroy()` already runs the synchronous cleanup; Plan 8.5b-02 registers an `undoManager.clear()` hook on `disableCollab()` in `src/lib/collab/index.ts` so orphaned references never outlive the session.
   - Memory retention is acceptable within a single session (bounded by undo-stack depth); cross-session retention is prevented by the teardown clear.

3. **RESOLVED: Is the recursive `createAnnotationSyncPlugin` factory safe to instantiate at nested-editor-mount time, or must it be pre-registered on collab enable?**
   - Decision: Safe to instantiate at mount time. No race between observeDeep install and teardown on rapid modal open/close.
   - Why: `NestedEditorController.destroy()` is synchronous (see existing controller pattern in `src/lib/editor/plugins/annotations/NestedEditorController.ts`) — `unobserveDeep` completes before the CM view destroy call returns. A rapid open→close→reopen sequence serialises through the JavaScript event loop, so the second mount cannot observe a partially-torn-down previous instance.
   - Plan 8.5c-01 adds `scopeAnnotations.unobserveDeep(this.deepObserver)` inside the plugin's `destroy()` (already drafted in Plan 8.5b-01's ViewPlugin class).

4. **RESOLVED: Should `thread` also be a Y.Array at the version level, or only at the annotation level?**
   - Decision (per D-92 recursive shape + D-93): Per-annotation thread only. The `thread: Y.Array<MessageObject>` lives on each `YjsAnnotationNode` (the annotation's own Y.Map), NOT on each version Y.Map.
   - Why: Threads are comments ON the annotation, not on a specific version of it. Comments nested inside a revision body become their own annotations (recursive D-92 shape), each with its own `thread`. Version Y.Maps therefore carry `{ text: Y.Text, label?, annotations: Y.Map<YjsAnnotationNode> }` only — no redundant thread.
   - Plan 8.5a-02's `codeMirrorToYjsAnnotation` implements exactly this layout (thread set on the outer node; each version Y.Map has `text` + `annotations` but no `thread`).
