# Linking Revision Versions Together (#268)

## Goal

Let a user link a version of one revision annotation to versions of *other*
revision annotations, so they form a matched set. Switching to any member of the
set switches every other member to its partner automatically.

**Concrete example.** A doc has Revision A (intro) and Revision B (conclusion),
each with a "Formal" and a "Casual" version. The user links `A.formal` +
`B.formal` into a group named *Formal*, and `A.casual` + `B.casual` into
*Casual*. Now clicking the Casual pill on A also flips B to Casual in one
undoable step.

## Decisions (confirmed)

| # | Decision |
|---|----------|
| 1 | **Auto-switch.** Activating a group member switches all members — a real, undoable doc edit. |
| 2 | **Named groups (sets).** A group spans multiple revisions; each contributes one version. |
| 3 | **Exclusive membership.** Each version belongs to at most one group. |
| 4 | **Stable version IDs first.** Migrate versions from array index → stable `id`, then build groups on top. |
| 5 | **Top-level `versionGroups` map** in the annotation state — groups are first-class. |
| 6 | **Two PRs.** PR 1 = version-ID migration (no UX change). PR 2 = the feature. |
| 7 | **Minimal UI first.** Pill affordance + group badge; defer a dedicated panel. |

---

## Why version IDs first

Today a "version" has no stable identity — `activeVersionIndex: number` is an
array index, and the param named `versionId` throughout the code is *also* just
the index. A link stored as `{ revisionId, versionIndex }` would silently rot:
deleting or reordering a version shifts indices and the link points at the wrong
text. The model file even carries the hint `// this will now refer to an ID`
next to `activeVersionIndex`.

So PR 1 is a pure, behavior-preserving refactor that gives every `VersionState`
a stable `id` and threads it everywhere an index is used today.

## PR 1 — Stable version IDs (refactor, no user-visible change)

### Data model (`models.ts`)

```ts
export type VersionState = object & {
    id: string;        // NEW — stable, unique within a revision
    doc: string;
    label?: string;
};

type RevisionAnnotation = BaseAnnotation & {
    _type: "revision";
    activeVersionId: string;   // was activeVersionIndex: number
    versions: VersionState[];  // order still meaningful for pill display
};
```

- IDs are short opaque strings (`v` + counter or short random). Generated by a
  new `newVersionId()` helper. Uniqueness only needs to hold **within one
  revision's `versions[]`**, so a per-revision counter is sufficient and
  collab-safe (collab already prefixes annotation IDs by client; we mirror that
  by including a small random/client component to avoid cross-client collisions
  when two users add a version concurrently).
- `versions[]` stays an **ordered array** — pill order and `Ctrl-[`/`Ctrl-]`
  navigation still use position. Only *identity* moves to `id`.

### Helpers (new, in `models.ts` / `utils.ts`)

```ts
newVersionId(): string
versionIndexById(rev, id): number          // -> index or -1
activeVersionIndex(rev): number             // versionIndexById(rev, rev.activeVersionId)
versionById(rev, id): VersionState | undefined
```

Index-based callers that are *purely positional* (pill rendering, next/prev
navigation, modulo cycling) keep using indices via these helpers. Callers that
**identify** a specific version (effects, deletes, switch target, labels) move to
IDs.

### Effects & commands (`annotationField.ts`)

Change the *target* of these from index to `versionId: string`:

- `_deleteVersionFromRevision` — `{ annotationId, versionId: string }`; delete by
  `id`, recompute `activeVersionId` (if the active one was deleted, fall to the
  neighbor by position).
- `_updateActiveRevisionVersion` — `{ annotationId, to: string }`; selection
  rebuild uses `versionById`.
- `_updateRevisionVersionState` / `_updateRevisionVersionDoc` /
  `_updateRevisionVersionLabel` — target by `id`.
- `_addVersionToRevision` — newly-added version already has an `id`; keep
  optional positional `at?` for insertion order. New active = the new id.

Public builders change signature: `setActiveRevisionVersion(state, annId, toId)`,
`deleteRevisionVersion(state, annId, versionId)`, etc. — callers pass
`version.id` instead of a loop index.

`pushDocToVersionState` (Phase 3) reads/writes
`versions[activeVersionIndex(x)]` via the helper — no behavior change.

**Undo inversion** (`invertedAnnotationFieldEffects`): each inverse now restores
by `id` (and re-inserts deleted versions at their old position so pill order is
preserved). The version object already carries its `id`, so add/delete inversion
is exact.

### Navigation (`index.ts`, `nestedEditor.ts`, `RevisionModal.svelte`)

`Ctrl-[`/`Ctrl-]` and modal cycling compute the next **index** with the existing
modulo math, then translate to an id: `setActiveRevisionVersion(state, id,
versions[nextIndex].id)`.

### Collab (`collab/annotationSchema.ts`, `yjsAnnotations.ts`, `types.ts`)

- Stop keying the versions `Y.Map` by `String(idx)`. Key by the stable
  `version.id`. Store an explicit `order: Y.Array<string>` (or an `index` field
  per version) so pill order survives — Y.Map has no guaranteed key order.
- Store `activeVersionId: string` instead of `activeVersionIndex: number`.
- `yjsAnnotationToCodeMirror` reads versions in `order`, attaching each `id`.
- `syncRevisionVersions` / `syncAnnotationFields` diff by `id`, not index.
- The whole-revision-rebuild path on a version switch is unchanged (still keyed
  on the annotation node).

### Clipboard (`clipboardAnnotations.ts`, `SerializedAnnotationSchema`)

- Serialized revision carries `activeVersionId` + `versions[]` (each with `id`).
- On **paste**, regenerate fresh version IDs (like annotation IDs are
  regenerated) to avoid collisions with existing versions, and remap
  `activeVersionId` to the regenerated id. (Groups are not copied in PR 1.)

### Export (`export.ts`) & restore (`restore.ts`)

- Export: mark the active version by `id` comparison instead of `i === index`.
  JSON/MD/PDF output shape unchanged except the "active" marker source.
- Restore/heal: read active text via `versionById(ann, ann.activeVersionId)` with
  a fallback to `versions[0]` when the id is missing (back-compat).

### Backward compatibility / migration

**Where the data actually lives.** Local SQLite never parses version data — the
`events` and `snapshots` tables store opaque `state.toJSON(savedFields)` blobs
(CodeMirror state JSON). So the "local SQL migration" is **not** a `migrations.rs`
schema change; it's a **JS-side normalization at the load/replay boundary**
(`annotationField.fromJSON` + the event-replay path). Old blobs heal themselves
into the new shape the first time they're read, and re-snapshot in the new shape.
No Rust change is required for the blob format. (If we later want eager rewrite
rather than lazy heal-on-load, that's a separate Rust pass; not needed now.)

**Web Preview / public share compatibility (the drafts+tabs-style workaround).**
The read-only Web Preview is the Supabase public share built by
`sharePayload.ts`. Its wire shape — `SerializedRevisionAnnotation` with
`activeVersionIndex: number` and `versions[].index` — is consumed by the landing
repo's renderer, which we are NOT changing now. So the share serializer keeps
emitting the **index-based shape**: derive `activeVersionIndex` from
`activeVersionId` (`versionIndexById`) and keep `versions[].index` at
serialization time. The new stable `id` is simply not surfaced in the share
payload yet. This mirrors how the share stays document-keyed to avoid forcing the
preview to learn about tabs/drafts — the internal model evolves, the public
contract doesn't.

**Collab/Omni live system.** Minimal changes only (read-tolerant: accept both
`activeVersionIndex` and `activeVersionId`, both `String(idx)` and id-keyed
version maps). The full id-native rewrite of the Yjs schema is tracked in a new
GH issue rather than done here.

Persisted documents have versions with **no `id`** and revisions with
`activeVersionIndex`. Add a one-time normalization at load (in `fromJSON` and the
Yjs read path):

- If a version lacks `id`, assign `newVersionId()` deterministically by position.
- If a revision has `activeVersionIndex` but not `activeVersionId`, set
  `activeVersionId = versions[clampedIndex].id`.

`VersionStateSchema` / `RawAnnotationSchema` accept both shapes during a
transition: `id` optional in the raw schema, `activeVersionId` optional and
`activeVersionIndex` optional, with the normalizer guaranteeing the runtime
invariant (every version has an id, every revision has a valid `activeVersionId`).
The `.passthrough()` already in place keeps unknown keys safe.

### Tests (PR 1)

- Unit: create → add version → switch → delete (active and non-active) → undo
  chain, asserting `activeVersionId` correctness and pill order.
- Migration: load a legacy snapshot (index-based) and assert normalization gives
  every version an id and a valid `activeVersionId`.
- Clipboard: copy revision → paste → version ids regenerated, active preserved.
- Existing revision/nested-editor tests must stay green (behavior identical).

**PR 1 ships when:** `bun run check`, `bun run test:run`, and the revision/collab
test suites are green, with behavior identical to today.

## PR 2 — Version groups (the feature)

Built entirely on PR 1's stable IDs.

### Data model

Add a sibling structure to the annotation map. The `annotationField` becomes a
small wrapper holding both:

```ts
export type VersionGroupMember = { revisionId: number; versionId: string };
export type VersionGroup = {
    id: string;
    label: string;
    members: VersionGroupMember[];
};
export type VersionGroups = { [groupId: string]: VersionGroup };
```

Storage options considered: a separate `StateField<VersionGroups>` vs. folding
into `annotationField`. **Chosen:** a dedicated `versionGroupField:
StateField<VersionGroups>` next to `annotationField`. Keeps the heavily-tested
annotation reducer untouched and gives groups their own clean
effect/undo/serialize surface. (The user-facing "top-level map" decision is
satisfied either way; a separate field is the lower-risk realization.)

Invariants enforced by the reducer:
- **Exclusive membership.** Adding `(rev, ver)` to a group removes it from any
  other group first.
- **Referential integrity.** When a revision is deleted, or a version is deleted,
  prune matching members. If a group drops below 2 members it's auto-dissolved
  (a group of one links nothing).

### Effects (`versionGroupField.ts`)

```ts
_createVersionGroup   { group: VersionGroup }
_deleteVersionGroup   { groupId }
_addMemberToGroup     { groupId, member }     // removes member from prior group
_removeMemberFromGroup{ groupId, member }
_renameVersionGroup   { groupId, label }
```

Each with an inverse for undo (mirrors the annotation-field pattern). Membership
moves are invertible because we capture the prior group on the effect.

### Auto-switch behavior

The coupling lives in **one place**: when an `_updateActiveRevisionVersion`
effect is dispatched for `(revId → versionId)`, look up that member's group; for
every *other* member `(otherRev, otherVer)` whose current active version differs,
emit an additional `_updateActiveRevisionVersion` for `otherRev → otherVer`
**plus the corresponding doc change** in the **same transaction**.

- Implemented as a small transaction extender: a function
  `withGroupCascade(state, primarySwitchSpec)` that expands one switch into the
  full set, building all the doc `changes` and effects together. `Ctrl-[/]`,
  pill clicks, and modal switches all route through `setActiveRevisionVersion`,
  so they get cascade for free if the builder applies it.
- **Loop/cycle guard.** Cascade only switches members that aren't already on
  their target version; since membership is exclusive and a single group switch
  has one target per revision, there's no oscillation. A `cascadeGuard`
  transaction annotation prevents re-entrancy.
- **Atomicity & undo.** All switches are in one transaction → one undo step
  reverts the whole group. This matches decision #1's preview.

### Collab (PR 2)

- Register a new top-level `ydoc.getMap("versionGroups")` (parallel to
  `"annotations"`), wired through `yjsProvider` → `enableCollab` →
  a `createVersionGroupSyncPlugin` (same shape as the annotation sync plugin:
  deep observer in, diff-and-reconcile out, `local`-origin guard).
- Group switches are already multi-revision CM transactions; the existing
  annotation sync writes each revision's `activeVersionId` inside one
  `ydoc.transact("local")`, so peers receive the group switch atomically.
- Concurrent edits to the *group structure* converge via Yjs LWW on the group
  map (same model as everything else; acceptable for dogfooding).
- Add `versionGroups` to the readonly **share payload** (`sharePayload.ts`) and a
  `published_version_groups` column (or nest in existing JSON) so shared docs
  render linked sets. (Can be a stretch item.)

### UI (minimal, per decision #7)

In `Revision.svelte` (and mirrored in `RevisionModal.svelte`):

- Version pill overflow menu gains **"Link to group ▸"** → submenu listing
  existing groups + "New group…". Selecting adds `(thisRev, thisVersion)` to the
  group.
- A linked pill shows a small group badge (◈) tinted per group; hover/title shows
  the group label and its members.
- "Unlink" removes the member.
- No dedicated groups panel yet (deferred).

### Tests (PR 2)

- Group create → add members across 2–3 revisions → switch one → assert all
  members switched, one undo reverts all.
- Exclusive membership: adding a version already in group X to group Y removes it
  from X.
- Integrity: delete a revision / a version → members pruned, group dissolved at
  <2.
- Undo across group create/add/switch/delete.
- Collab: two clients, one creates a group and switches; the other converges.

## Risk notes

- The migration touches ~110 sites across local + collab + clipboard + export +
  restore. Isolating it in PR 1 (no UX change) makes any regression bisectable.
- The single most dangerous spot is the Yjs version keying (`String(idx)` →
  stable id + explicit order). It gets dedicated tests and a legacy-load test.
- Auto-switch is concentrated in one cascade builder so the coupling logic is
  testable in isolation and can't leak re-entrancy.

## Out of scope (for now)

- Cross-nesting-level links (a version inside a nested revision linking out).
  IDs are per-editor-level; a qualified ref would be needed. Deferred.
- Dedicated groups management panel.
- Sharing groups in the public readonly view (stretch).

## What shipped (PR 2)

Built as planned, with these concretizations:

- **Storage:** a dedicated `versionGroupField: StateField<VersionGroups>` (the
  separate-field realization), registered in the `annotations()` bundle and
  `savedFields` (persisted). Effects + public transaction builders
  (`createVersionGroup` / `addVersionToGroup` / `removeVersionFromGroup` /
  `deleteVersionGroup` / `renameVersionGroup`).
- **Invariants in the reducer:** exclusive membership (add detaches from prior
  group), one version per revision per group (`canAddMemberToGroup`), and
  referential integrity (revision/version delete prunes members; a group below
  two members dissolves). Undo uses a **snapshot-restore** inversion
  (`_restoreVersionGroups`) — one effect restores the pre-transaction map,
  uniformly correct for structural ops AND integrity prunes triggered by
  annotation effects.
- **Cascade:** folded directly into `setActiveRevisionVersion` via
  `groupSwitchTargets` — a switch on a grouped version expands to all partners'
  switches + doc changes in one transaction, so every switch path (pill,
  `Ctrl-[/]`, modal) cascades for free and reverts in one undo. The
  annotationField ↔ versionGroupField import pair is a safe ESM cycle
  (function-body-only cross-refs).
- **UI:** inline version-pill link button + dropdown ("Link to another
  revision…", "Join \<group\>", "Unlink") and a per-group colored badge dot on
  linked pills. Because a group spans revisions, linking is a **two-pick flow**
  via a shared `linkAnchor` store (anchor on one revision's pill, complete on
  another's). Modal pill mirror deferred.
- **Collab deferred** to #273 (group *switches* already sync atomically via the
  existing annotation sync; only the group *structure* map is unsynced). Pairs
  with #269.

Tests: `tests/annotations/versionGroups.test.ts` — cascade (both directions),
one-undo-reverts-all + redo, ungrouped independence, exclusive membership,
one-version-per-revision, integrity prune/dissolve, undo-restore of a dissolved
group.
